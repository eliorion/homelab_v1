# keycloak-operator

The Keycloak project's own operator, vendored into this repository. It owns the
`Keycloak`, `KeycloakRealmImport`, `KeycloakOIDCClient` and `KeycloakSAMLClient`
CRDs, and reconciles the `Keycloak` CR declared in
`infrastructure/services/base/keycloak/app/`. Every other controller in
`infrastructure/controllers/` is a HelmRelease; this one cannot be, because the
Keycloak project publishes no Helm chart for its operator — the supported
installs are the raw release manifests or an Operator Lifecycle Manager this
cluster does not run. So the release manifests live in git under `upstream/`
and are applied as a plain kustomize base.

Deep detail on the whole Keycloak stack lives in
[`../../../../documentations/02-keycloak.md`](../../../../documentations/02-keycloak.md);
the vendoring decision is recorded in
[`../../../../documentations/14-design-decisions.md`](../../../../documentations/14-design-decisions.md)
("The Keycloak operator is vendored into this repository").

## How it is wired

| File | What it is |
|---|---|
| `kustomization.yaml` | Lists the five vendored files plus `namespace.yaml`, sets `namespace: identity`, and runs the `NamespaceTransformer` that retargets upstream's `keycloak` namespace. Carries the current version as `# keycloakOperatorVersion:` and the Renovate datasource annotation. |
| `namespace.yaml` | The `identity` Namespace object. This component owns it. |
| `upstream/kubernetes.yaml` | Vendored, verbatim. The `keycloak-operator` ServiceAccount, five ClusterRoles, the `keycloak-operator-clusterrole-binding` ClusterRoleBinding, the namespaced `keycloak-operator-role` plus six RoleBindings, a Service, and the `keycloak-operator` Deployment (`quay.io/keycloak/keycloak-operator:26.7.0`, one replica, liveness/readiness/startup probes on `:8080` `/q/health/*`). |
| `upstream/keycloaks.k8s.keycloak.org-v1.yaml` | Vendored CRD for `Keycloak` (`kc`), `v2beta1`, namespaced. |
| `upstream/keycloakrealmimports.k8s.keycloak.org-v1.yaml` | Vendored CRD for `KeycloakRealmImport`, `v2beta1`, namespaced. |
| `upstream/keycloakoidcclients.k8s.keycloak.org-v1.yaml` | Vendored CRD for `KeycloakOIDCClient`, `v2alpha1`, namespaced. |
| `upstream/keycloaksamlclients.k8s.keycloak.org-v1.yaml` | Vendored CRD for `KeycloakSAMLClient`, `v2alpha1`, namespaced. |

Everything under `upstream/` is a byte-identical copy of the release, generated
by the Fabric8 CRD generator and by Quarkus. Their header comments
(`# Generated by Fabric8 CRDGenerator, manual edits might get overwritten!`) are
upstream's, not this repository's, and are left untouched.

`scripts/fetch-keycloak-operator` (repo root, outside this directory) is the
only supported way to change `upstream/`.

### Overlays

There is no `staging/` or `production/` overlay for this component. Flux applies
the base directly: `clusters/staging/infrastructure.yaml` declares a
Kustomization `infra-keycloak-operator` with
`path: ./infrastructure/controllers/base/keycloak-operator`, `wait: true` and a
health check on the `keycloak-operator` Deployment in namespace `identity`.

Ordering, per doc 02: `infra-keycloak-operator` (CRDs + namespace + operator) →
`infrastructure-services` (database + `Keycloak` CR) → `infra-keycloak-realm`
(the keycloak-config-cli import Job).

## Why it is like this

**Vendored, not remote.** The alternative to committing the manifests was a
remote kustomize base pointing at `raw.githubusercontent.com`. That would make
every Flux reconcile depend on GitHub being reachable, and would let a re-tagged
release change what the cluster runs without a commit. Roughly 950 KB of
generated CRD YAML under `upstream/` is the price of neither being true, and it
keeps the operator reviewable in a PR like everything else here.

**Not a HelmRelease, not a StatefulSet.** No community chart is used. Keycloak
here used to be a hand-written StatefulSet; the operator replaced it because
Infinispan/JGroups discovery, ordered rolling updates and the generated Service
all fall out of `instances: 2` instead of being hand-maintained.

**`.yaml`, not `.yml`.** Upstream publishes these five files as `.yml` — there is
no `.yaml` to fetch, that URL 404s. The fetch script renames on download so the
files match every other manifest in the repo. Only the extension changes; the
content stays byte-identical to upstream, so a bump stays a reviewable diff.

**Namespace-scoped, in `identity`.** The operator's Role and RoleBinding are
namespaced, so it reconciles `Keycloak` CRs only in the namespace it runs in. It
runs in `identity` beside the Keycloak it manages, and owns that Namespace
object — `infrastructure/services/base/keycloak` deliberately no longer declares
it, so two Flux Kustomizations never fight over the same resource. Upstream
ships the manifests for a namespace called `keycloak`; the `NamespaceTransformer`
in `kustomization.yaml` retargets them.

The cluster-wide variant (`kubernetes/cluster-wide/` in the release) exists for a
multi-namespace estate. One Keycloak does not need it, and it would trade a
namespaced Role for cluster-wide write access to every `Keycloak` CR.

**One version knob.** The server version follows the operator: the `Keycloak` CR
deliberately sets no `spec.image`, so the operator runs the server it shipped
with (`RELATED_IMAGE_KEYCLOAK: quay.io/keycloak/keycloak:26.7.0` in its
Deployment). No operator/server skew to track.

**No realm configuration here.** The operator's `KeycloakRealmImport` CR is
create-oriented, so realm updates are effectively ignored. The realm is applied
by keycloak-config-cli instead — see
`infrastructure/services/base/keycloak/realm/`. Its CRD is still installed
because the operator registers a controller for it and would error without it.

## Traps

- **Do not hand-edit anything under `upstream/`.** Bump with
  `scripts/fetch-keycloak-operator <version>`; a hand-edited vendored CRD makes
  the next bump an unreviewable diff.
- **`setRoleBindingSubjects: allServiceAccounts` in the `NamespaceTransformer` is
  load-bearing.** Without it the ClusterRoleBinding still points at
  `system:serviceaccount:keycloak:keycloak-operator`, the operator starts with no
  permissions, and it reconciles nothing while looking perfectly healthy.
- **`# keycloakOperatorVersion:` in `kustomization.yaml` is machine-read.** It is
  the Renovate anchor and the line the fetch script rewrites with `sed`
  (`s|^# keycloakOperatorVersion: .*|...|`). Do not reword or reformat it, and
  do not move the `# renovate: datasource=github-releases
  depName=keycloak/keycloak-k8s-resources` line away from it.
- **The `identity` Namespace is declared here and nowhere else.** Re-adding it to
  `infrastructure/services/base/keycloak` puts two Flux Kustomizations on the
  same object.
- **Do not set `spec.image` on the `Keycloak` CR** to "match" a bump. Setting it
  makes the operator assume a pre-optimized image and start with `--optimized`,
  and it decouples the server from the operator.
- **The vendored filenames end in `.yaml`, and `kustomization.yaml` lists them
  that way.** An older checkout vendored the upstream `.yml` names; leaving both
  around applies every CRD twice, which is why the fetch script removes
  `upstream/*.yml`.
- **keycloak-config-cli lags the server.** Its newest version-specific image is
  built against 26.5.5, so the realm Job runs the floating `6.5.1-26` tag. If the
  realm pipeline breaks after an operator bump, that skew is the first suspect
  (doc 02).

## Operating it

Bump the operator (and, with it, the server):

```bash
scripts/fetch-keycloak-operator 26.7.0
```

The script downloads all five files to a temp dir first, so a 404 on the last
one cannot leave the component half-bumped — a new operator against old CRDs.
It then rewrites `# keycloakOperatorVersion:` and prints the resolved
`quay.io/keycloak/keycloak-operator` image line for review.

Render check before committing, and watch the reconcile:

```bash
kubectl kustomize infrastructure/controllers/base/keycloak-operator
flux get kustomizations infra-keycloak-operator
kubectl -n identity get deploy keycloak-operator
kubectl -n identity logs deploy/keycloak-operator
```

If the operator is `Ready` but nothing happens to the `Keycloak` CR, check the
ClusterRoleBinding subject first — that is the `setRoleBindingSubjects` failure
mode above:

```bash
kubectl get clusterrolebinding keycloak-operator-clusterrole-binding -o yaml
```
