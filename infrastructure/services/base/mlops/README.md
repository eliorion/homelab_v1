# mlops

The shared MLOps platform of the asp repo (plan: asp `docs/24-scout-matchmaking-mlops-plan.md`):
**Dagster** orchestrates pipelines, **MLflow** tracks runs, evaluations and model versions. Both
web UIs are on the tailnet only:

| UI | URL | Gate |
|---|---|---|
| Dagster | https://dagster.tail45b0ca.ts.net | the tailnet only — Dagster OSS has no login |
| MLflow | https://mlflow.tail45b0ca.ts.net | the tailnet + MLflow `basic-auth` (user `admin`) |

Every ML workload runs **here** (asp docs/27 D1, D2), from one image, `mlops-pipelines`: its code
locations (chart `k8s/charts/mlops-pipelines`, `release-pipelines.yaml`) and the run pods Dagster
launches beside them. A domain (fbref today) provides a read-only database role and the schema its
published results land in; its role Secrets are reflected here. Two locations: **`mlops-pipelines`**, production
(the fbref lake extract, the step-up model and its publication, asp docs/25), and
**`mlops-pipelines-dev`**, the dev lane (`extract_query`, `run_notebook`; read-only credentials, one run
at a time through the `mlops/lane: dev` tag limit in `release-dagster.yaml`). The domain side is wired
in `apps/staging/fbref/README.md`.

## How it is wired

| Object | File | What |
|---|---|---|
| Namespace `mlops` | `namespace.yaml` | label `name: mlops` |
| HelmRelease `dagster` | `release-dagster.yaml` | upstream `dagster/dagster` chart, pinned: webserver + daemon as uid 1000 on a read-only root, K8sRunLauncher, storage on `mlops-db`, telemetry off, no user-code subchart |
| HelmRelease `mlops-pipelines` | `release-pipelines.yaml` | asp chart `k8s/charts/mlops-pipelines` (GitRepository `mlops-pipelines`, `clusters/staging/sources.yaml`): one gRPC code server per location and the run pods' shape (service account `<location>-run`, no API token; its own NetworkPolicies) |
| HelmRelease `mlflow` | `release-mlflow.yaml` | the **official** chart `oci://ghcr.io/mlflow/charts/mlflow` with the official `ghcr.io/mlflow/mlflow:vX.Y.Z-full` image (Postgres driver, boto3 and the auth extras built in) |
| ConfigMap `dagster-workspace` | `dagster-workspace.yaml` | the code locations Dagster loads: `mlops-pipelines.mlops.svc.cluster.local:3030` |
| ConfigMap `mlflow-auth-config` | `mlflow-auth-config.yaml` | MLflow's `auth.ini`, secret-free: its store URI has no host or password (libpq reads the `PG*` variables from `mlops-db-app`) and the admin password comes from `MLFLOW_AUTH_ADMIN_PASSWORD` |
| Policies | `networkpolicies.yaml` | ingress to both UIs from the Tailscale proxy and Homepage only, and to MLflow from the code locations' run pods (`app=mlops-pipelines-run`); MLflow egress to its database, SeaweedFS and DNS; Dagster egress to DNS, its database, the code locations' gRPC servers and the Kubernetes API |
| Ingresses `dagster`, `mlflow` | `ingress-tailscale.yaml` | Tailscale operator, HTTPS 443 |
| CNPG `mlops-db` | `../databases/mlops/` | 1 instance; databases `mlflow` (initdb), `mlflow_auth`, `dagster`; role `mlflow` = the initdb owner, its login **generated by CNPG** as `mlops-db-app`; role `dagster` managed from its OpenBao Secret |
| Credentials | `../../staging/mlops/secrets/` | MLflow's database login: CNPG's `mlops-db-app`. The rest: ExternalSecrets from OpenBao `kv/mlops/*` |
| Bucket `mlflow-artifacts` | `controllers/staging/seaweedfs/s3/` | in-cluster SeaweedFS, identity scoped to that bucket, Secret `s3-mlflow-artifacts` reflected into `mlops` |

### Credentials

MLflow's database login is the one CNPG generates for the initdb owner: Secret `mlops-db-app`
(`uri` for the runs store, `host`/`port`/`username`/`password` for the auth store), the same way
asp and fbref read `asp-db-app` / `fbref-db-app`. OpenBao holds only what CNPG cannot generate:

| OpenBao path | Keys | Becomes |
|---|---|---|
| `kv/mlops/mlflow-auth` | `admin-password`, `flask-secret-key` | `mlflow-auth`: the first admin password (`MLFLOW_AUTH_ADMIN_PASSWORD`) and the CSRF key |
| `kv/mlops/dagster-db` | `password` | `mlops-dagster-db`: username, password (CNPG managed role) and `postgresql-password` (the dagster chart and every run pod, all in this namespace) |
| `kv/mlops/ml-ro` | `password` | `ml-ro`: the ML platform's ONE database reader `ml_ro` (asp docs/27 D10), the same role and password on fbref-db, asp-db and advisor-db. Reflected to `fbref`, `asp` and `advisor`, where CNPG sets the role's password from it; the run pods read it here (`PGPASSWORD`) |
| `kv/mlops/mlflow-notebook` | `password` | `mlops-mlflow-notebook`: the MLflow user `notebook`, for the dev location's runs and `mise run notebook` in the asp devcontainer (asp docs/27 P2) |

**Seed them before the first reconcile** (hex only). Login as in `../openbao/README.md`, then:

```sh
bao kv put kv/mlops/mlflow-auth admin-password="$(openssl rand -hex 24)" flask-secret-key="$(openssl rand -hex 32)"
bao kv put kv/mlops/dagster-db  password="$(openssl rand -hex 32)"
```

The ML reader (asp docs/27 D10), before the first reconcile of `ml-ro` (until it exists, CNPG keeps
`ml_ro` without a password on the three databases and every extract fails to log in):

```sh
mise bao kv put kv/mlops/ml-ro password="$(openssl rand -hex 32)"
```

The in-cluster marimo notebook (asp docs/27 P11) has no login, like Dagster: the tailnet (owner only) is
its gate. Anyone on the tailnet can run code there with the dev lane's read-only database credentials and
the lake key, the same exposure Dagster's UI already has.

The dev lane's MLflow user (asp docs/27 P2), once MLflow runs:

```sh
mise bao kv put kv/mlops/mlflow-notebook password="$(openssl rand -hex 32)"
mise mlflow-user notebook kv/mlops/mlflow-notebook
```

It creates its own experiments (`notebooks`, ...); reading another user's experiment (`scout-stepup`)
needs a READ grant from the admin in the MLflow UI. Until it exists, dev runs still start and a
notebook that logs to MLflow is refused (401).

Without them the ExternalSecrets stay `SecretSyncedError`, the `dagster` role and both releases wait
and retry; nothing breaks, nothing starts.

## Why it is like this

- **Official MLflow chart and image.** The `-full` image already carries the drivers, so nothing is
  built or installed at start. The chart's defaults are already non-root uid 1000, read-only root,
  all capabilities dropped. Two gaps are filled here: the chart runs no schema migration (the
  `db-upgrade` init container, same image tag), and its NetworkPolicy admits every pod of every
  namespace (disabled; `networkpolicies.yaml` instead).
- **MLflow hardening.** `basic-auth` with `default_permission = NO_PERMISSIONS`; a Host-header
  allowlist (`allowed_hosts`: the in-cluster names and the tailnet device); the job runner off
  (`MLFLOW_SERVER_ENABLE_JOB_EXECUTION=false`: ~1.5 GiB of huey workers, unused, and the API
  surface of CVE-2026-0545); never below v3.15.0 (CVE-2026-64849, an SSRF the egress policy also
  blunts). Artifacts are proxied (`--serve-artifacts`), so MLflow is the only holder of the bucket key.
- **Artifacts on SeaweedFS, never Garage.** Garage is off-site, low-bandwidth and small, kept for
  disaster-recovery data.
- **`mlops-db` is backed up to Garage** (bucket `cnpg-staging-mlops`, daily 04:00 UTC, 7d, WAL
  archived; staging overlay `infrastructure/services/staging/databases/mlops`, 2026-10-28).
  One instance: staging memory is short, so the backup is the only second copy.
- **Separate database roles.** MLflow, the component with the CVE history, cannot read Dagster's
  storage, which decides which Jobs the run launcher creates.
- **MLflow's database login from CNPG, the rest in OpenBao.** A login CNPG generates needs no seeding
  and is how every app here reads its database; OpenBao keeps the house rule for the credentials CNPG
  cannot make. The bucket key alone stays sops: the SeaweedFS identity file is assembled by Flux
  substitution from `flux-system` Secrets.
- **The releases do not depend on each other.** Dagster's pods mount `dagster-workspace`, which is
  plain here, so neither waits on the other.
- **Runs execute here, not in the domain's namespace** (asp docs/27 D2). The location's chart hands
  Dagster a container context (this namespace, the image, a service account without token, the
  secrets), so Dagster's own Role covers the run Jobs and no other namespace grants anything. The
  domain roles' Secrets stay where CNPG reads them (`fbref`) and are reflected here; the lake key
  (`s3-ml-lake`) is reflected here from `flux-system`. The storage host stays a FQDN
  (`mlops-db-rw.mlops.svc.cluster.local`): the launcher passes this instance config to the run as is.
- **The pods read the workspace at start only.** `mlops.eliorion.fr/workspace` on both Deployments
  names the code locations; change it with `dagster-workspace.yaml` so the edit rolls them.
- **Dagster ships on `tag:k8s`** like every operator device, and stays there with code locations
  loaded (owner, 2026-10-13: only the owner and the agent are on the tailnet). Its UI launches runs
  that read the whole fbref database: if anyone else ever joins the tailnet, move both Ingresses to a
  `tag:mlops` granted to the owner only first.

## Operating it

- **Rotate Dagster's database password:** `bao kv put` a new value. Within the hour the ExternalSecret
  updates and CNPG re-keys the role (`cnpg.io/reload`); restart Dagster to pick it up. MLflow's login
  follows CNPG's own procedure for the initdb owner (`mlops-db-app`); restart MLflow after it.
- **The MLflow admin password only seeds the first start.** Rotate it in the MLflow UI, then update
  `kv/mlops/mlflow-auth` so it stays the break-glass (the variable is read at the first start only).
- **Bump MLflow:** chart `version` and both image tags in `release-mlflow.yaml` move together.
- **An MLflow user for a code location** (its password in OpenBao, hex):
  `mise mlflow-user <user> kv/<namespace>/<entry>` (`scripts/mlflow-user`: reads both passwords
  through `mise bao`, prints neither). A new user has no permission on anyone's experiment and MANAGE
  on the ones it creates.

## After merge (one manual step, as for every bucket)

The SeaweedFS S3 gateway reads its identity file at start only:
`kubectl -n seaweedfs rollout restart deployment seaweedfs-seaweedfs-s3`.
