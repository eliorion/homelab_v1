# Bootstrap the cluster

Bringing up the platform from bare hardware to a cluster that Flux is driving.

This is the Talos path. The original k3s path is gone; if you are looking for how the
migration off it was done, that is [06-k3s-retirement.md](06-k3s-retirement.md) and
[07-talos-ha-expansion.md](07-talos-ha-expansion.md). For why Talos rather than a general
purpose distribution, see
[14-design-decisions.md](14-design-decisions.md#talos-linux-instead-of-a-general-purpose-distribution).

**Order matters at two points**, and both are load bearing:

1. The Talos machine config must be applied **before** Flux installs Cilium. Doing it the
   other way deadlocked the live cluster on 2026-06-12
   ([08-cilium-cni-ingress-migration.md](08-cilium-cni-ingress-migration.md#10-incident--recovery-2026-06-12)).
2. The two manual Secrets in step 5 must exist **before** Flux reconciles, or a large part
   of the graph never becomes ready.

---

## 00. Hardware

Three machines on one L2 segment. They must share a segment because the API VIP is claimed
by ARP.

Sizing that the current cluster actually uses:

- install disk of at least 150 to 200 GiB (the live nodes have roughly 1 TB each)
- enough RAM for the control plane plus workloads on every node, since all three run both
- a static address plan: `192.168.1.101` to `.103` for the nodes, `.100` for the API VIP,
  and `.110` to `.130` left free for the Cilium address pool. Keep that pool out of the
  DHCP range and away from the VIP, because two ARP speakers on one segment will otherwise
  collide.

**Boot the nodes from a Talos factory image that carries the node extensions.** Longhorn
needs `iscsi-tools` and `util-linux-tools`. Those come from a factory schematic, and the
schematic id for each machine is recorded in `bootstraping/talconfig.yaml` next to that
node's install image. Booting stock Talos gives a cluster where Longhorn fails with
`failed to execute iscsiadm: No such file or directory`.

A node with no config sits in maintenance mode with an address from DHCP. That is the
state the next step expects.

## 01. Development environment

The whole toolchain (`talosctl`, `talhelper`, `flux`, `sops`, `age`, `helm`, `kubectl`,
`k9s`, `cloudflared`, `aws`, `gh`) is declared in `mise.toml` and installed by
`scripts/setup` when the devcontainer is created.

```bash
devpod up .
devpod ssh          # only if you did not configure an editor in DevPod
```

The environment is deliberately not pinned to exact tool versions; the versions that matter
are pinned in manifests instead. The consequence is written up in
[14-design-decisions.md](14-design-decisions.md#toolchain-in-misetoml-every-tool-at-latest).

## 02. Render and apply the machine configs

Node configuration is generated by talhelper from one input file. Never hand edit anything
under `bootstraping/clusterconfig/`; it is generated and gitignored.

```bash
cd bootstraping
SOPS_AGE_KEY_FILE=../clusters/staging/age.agekey talhelper genconfig

# always validate before applying
talosctl validate --config clusterconfig/Homelab_staging-staging-controlplane-1.yaml --mode metal
```

Apply to each node. `--insecure` is required only while the node is still in maintenance
mode and has no PKI of its own:

```bash
talosctl apply-config --insecure -n 192.168.1.101 \
  --file clusterconfig/Homelab_staging-staging-controlplane-1.yaml
talosctl apply-config --insecure -n 192.168.1.102 \
  --file clusterconfig/Homelab_staging-staging-controlplane-2.yaml
talosctl apply-config --insecure -n 192.168.1.103 \
  --file clusterconfig/Homelab_staging-staging-controlplane-3.yaml
```

> **Never regenerate `talsecret.sops.yaml`.** It holds the etcd CA, the machine CA and the
> Kubernetes CA. A new secret is a new PKI, which means existing node certificates stop
> validating, existing `talosconfig` and `kubeconfig` stop authenticating, and etcd members
> cannot re-form. Disaster recovery depends on rebuilding node configs from the *same*
> secret. It is committed, encrypted, on purpose.

Bootstrap etcd, **once, on one node only**:

```bash
talosctl bootstrap -n 192.168.1.101
talosctl kubeconfig
```

Point `talosconfig` endpoints at real node addresses, never at the VIP. The VIP depends on
etcd, and `talosctl` has to keep working when etcd is what is broken.

```bash
kubectl get nodes   # all three appear, all NotReady: there is no CNI yet
```

`NotReady` at this point is expected. Talos is configured with `cniConfig.name: none` and
`proxy.disabled: true`; Cilium arrives from Flux.

## 03. Install the CNI once, by hand

This is the one step that cannot be GitOps, and it is a consequence of a deliberate
decision: Cilium ships as a Flux HelmRelease rather than as a Talos inline manifest, so
that it is versioned, reviewable and bumpable by Renovate, and so that no CA key material
lands in git. The price is that a completely cold cluster needs one manual install before
Flux can reach anything.

```bash
cilium install --version 1.19.4 \
  --set k8sServiceHost=localhost --set k8sServicePort=7445
kubectl get nodes   # Ready
```

`k8sServiceHost=localhost` with port `7445` is KubePrism, the host network local API
balancer. It is what lets kube-proxy be removed, and it is host network, so it keeps
working when the pod network does not. Flux later reconciles the same chart from
`infrastructure/controllers/base/cilium` and converges on the same values, so there is no
drift.

The full chart values, and what each one is protecting against, are in
[08-cilium-cni-ingress-migration.md](08-cilium-cni-ingress-migration.md).

## 04. Repository and a GitHub token

Flux needs push and pull access to the repository. A classic personal access token with
`repo` scope is enough for the bootstrap:

```bash
export GITHUB_TOKEN=<your-token>
export GITHUB_USER=<your-username>
```

Prefer exporting it in the shell for the duration of the bootstrap rather than storing it
in a file. Note that `*.envrc` is gitignored precisely because these tokens tend to end up
there.

## 05. The two Secrets Flux does not create

Both are manual, once per cluster, and neither is produced by `flux bootstrap`. Create them
first: everything downstream depends on them.

### The SOPS age key

Secrets in this repository are encrypted with [SOPS](https://github.com/getsops/sops) and
an [age](https://github.com/FiloSottile/age) key. `.sops.yaml` holds only the **public**
recipients, so encrypting and committing is safe. At reconcile time Flux needs the matching
**private** key, and it reads it from a Secret named `sops-age` in `flux-system`.

```bash
kubectl create namespace flux-system
kubectl create secret generic sops-age -n flux-system \
  --from-file=age.agekey=/path/to/age-private-key.txt
```

The filename inside the Secret must end in `.agekey`.

> **Keep the private key safe.** It is the only thing that can decrypt the Keycloak
> credentials, the object storage credentials, the tunnel credentials, the database secrets
> **and the cluster PKI in `talsecret.sops.yaml`**. Lose it and the cluster cannot be
> rebuilt, snapshots or not, because etcd snapshots do not cover the Talos machine PKI.
> Verify that the public line in the key file matches the recipient in `.sops.yaml` before
> you trust it.

`.sops.yaml` defines more than one recipient, selected by path. Check which recipient
covers the path you are bootstrapping rather than assuming one key covers everything.

### The deploy key for the external chart repository

`clusters/staging/sources.yaml` declares four GitRepository objects that fetch application
charts from a separate private repository, all authenticating with a Secret named
`asp-deploy-key` in `flux-system`. Create it from an SSH key registered as a deploy key on
that repository:

```bash
flux create secret git asp-deploy-key \
  --url=ssh://git@github.com/eliorion/asp \
  --private-key-file=/path/to/deploy-key
```

Without it, those four sources fail permanently and every HelmRelease that depends on them
stays not ready.

## 06. Bootstrap Flux

```bash
flux bootstrap github \
  --owner=$GITHUB_USER \
  --repository=homelab_v1 \
  --branch=main \
  --path=./clusters/staging \
  --personal
```

`flux bootstrap github` is idempotent: it installs or upgrades the controllers, commits
`gotk-components.yaml`, registers a deploy key on the repository, and creates the
`flux-system` GitRepository and Kustomization pointing at the path you gave.

Reconciling takes a while on a cold cluster: Longhorn's Kustomization has a 15 minute
timeout precisely because the first image pull on a cold node is slow.

```bash
flux get kustomizations
flux get helmreleases -A
```

The order in which those become ready, and why, is
[01-architecture.md](01-architecture.md#the-reconcile-graph).

## 07. Verify

```bash
kubectl get nodes                       # 3 Ready
talosctl -n 192.168.1.101 etcd members  # 3 members, no learners
kubectl get ciliumloadbalancerippool    # the .110 to .130 pool exists
flux get kustomizations                 # all Ready=True
```

One check worth doing explicitly, because it is the failure that hides longest: confirm
that a workload with an encrypted Secret actually decrypted, rather than receiving the
literal `ENC[AES256_GCM,...]` string. A Kustomization missing its `decryption` block does
not error at apply time.

## A second cluster

One repository can drive several clusters. Each reconciles its own path and they cannot
conflict, because each only applies what is under its own path.

The steps are the same: install Talos on the new hardware, point `KUBECONFIG` at it and
**verify you are on the right cluster before doing anything**, create both Secrets from
step 5 using the recipient that covers that path, then bootstrap Flux against the other
path.

```bash
kubectl get nodes        # must show the new cluster, not staging

flux bootstrap github \
  --owner=$GITHUB_USER \
  --repository=homelab_v1 \
  --branch=main \
  --path=./clusters/production \
  --personal
```

Two things to know before doing that today:

- `clusters/production/flux-system/gotk-sync.yaml` still points at the repository's former
  name. It would need updating first.
- The production overlays have not been maintained since June 2026 and still encode a
  shared bucket layout that staging deliberately moved away from. Treat that tree as
  scaffolding, not as a ready second environment. See
  [14-design-decisions.md](14-design-decisions.md#10-open-work).

Seeding a second cluster's databases from the first is a one time CloudNativePG recovery
bootstrap: replace the Cluster's `initdb` with `bootstrap.recovery` pointing at the source
ObjectStore. The mechanics are in [03-backups.md](03-backups.md), and the rule that goes
with it is in
[14-design-decisions.md](14-design-decisions.md#never-archive-back-into-the-path-you-are-restoring-from):
never let the recovered cluster archive back into the path it was restored from.
