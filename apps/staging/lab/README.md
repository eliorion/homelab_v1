# lab

`lab` is the cluster's central analysis sandbox: one Jupyter pod per project, living in
its own `lab` namespace (`lab-asp`, `lab-fbref`, …), each reading its project's read-only
database replica across namespaces. It is a single `HelmRelease` driving a chart that fans out
over a `projects` list, so adding a sandbox is one line rather than one more copy of a
Deployment, a Service and a set of Secrets. The pods are published on the tailnet by the
Tailscale operator and are always on (`replicas: 1`), so a lab is reachable without scaling
anything up first.

## How it is wired

Flux Kustomization `lab` (`clusters/staging/lab.yaml`, namespace `flux-system`) reconciles
`./apps/staging/lab` from the `flux-system` GitRepository with `interval: 1m0s`,
`retryInterval: 1m`, `timeout: 10m`, `prune: true`, `wait: true`, and a health check on the
`lab` HelmRelease in `flux-system`. It `dependsOn` two things:

- `databases` — brings up the CNPG clusters, among them the two lab reads (`asp/` and
  `fbref/`), with their `<db>-app` Secrets and the reflection permit annotation.
- `infra-reflector` — the reflector controller that fills the chart-generated stub Secrets in
  the `lab` namespace.

`lab/` is deliberately absent from `apps/staging/kustomization.yaml`; it is its own Flux
Kustomization, not part of the `apps` tier.

Files in this directory:

- `kustomization.yaml` — lists the two resources below. Nothing else: the reflect-stub Secrets
  that used to live here are generated by the chart now.
- `namespace.yaml` — the `lab` namespace, with no PodSecurity opt-out label.
- `release.yaml` — `HelmRelease` `lab` in `flux-system`, `targetNamespace: lab`,
  `interval: 30m`, chart `k8s/charts/lab` from `sourceRef` GitRepository `lab` with
  `interval: 12h` and `reconcileStrategy: Revision`, `install.createNamespace: true`,
  install and upgrade remediation `retries: 3` with `strategy: rollback` on upgrade.

The chart itself is not in this repository. GitRepository `lab`
(`clusters/staging/sources.yaml`) points at `ssh://git@github.com/eliorion/asp`, branch `main`,
authenticated with the read-only `asp-deploy-key` Secret, `interval: 1m0s`, and an `ignore`
block scoped to `/k8s/charts/lab/` so unrelated `asp` commits do not churn the artifact.

Values set in `release.yaml`:

| value | setting |
| --- | --- |
| `replicas` | `1` — always on |
| `projects` | `asp`, `fbref` |
| `tailscale.expose` | `true` |
| `auth.disableToken` | `true` |
| `imagePullSecretReflect.enabled` | `true` |
| `imagePullSecretReflect.source` | `reflector/ghcr-pull-secret` |

Each lab is reached on the tailnet at `http://lab-asp.<tailnet>.ts.net:8888` and
`http://lab-fbref.<tailnet>.ts.net:8888`.

### Overlays

There is no `apps/base/lab/` and no production overlay — this staging directory is the whole
component. Everything environment-specific (which projects exist, tailnet exposure, the pull
secret source) is a value on the one HelmRelease, and the templating lives in the external
chart.

## Why it is like this

**One HelmRelease, a `projects` list, one pod per project.** The chart derives each lab's
database coordinates from the CNPG naming convention and generates that lab's reflect-stub
Secret, so a new sandbox is an entry in `projects` instead of a hand-written Deployment plus a
hand-written stub Secret in this directory. That is also why `kustomization.yaml` carries only
the namespace and the release.

**Always on rather than scaled to zero.** `replicas: 1` keeps every lab reachable on the tailnet
without scaling it up first; scaling to `0` is still the way to park one (see "Operating it").

**Tailnet identity is the auth boundary.** `auth.disableToken: true` removes the random Jupyter
token, the same model the admin UIs use: the lab is only reachable through the Tailscale
operator, so being on the tailnet is the authentication. The consequence is explicit — anyone on
the tailnet gets that lab's read-only database access.

**The private image is pulled without a public package.** `imagePullSecretReflect` makes the
chart generate a stub Secret in the `lab` namespace and adds it to the pods' `imagePullSecrets`;
the reflector controller fills that stub from the canonical `reflector/ghcr-pull-secret`. The
source secret already permits reflection into `lab` (its
`reflection-allowed-namespaces` lists `asp,fbref,lab,scraper`), so no per-namespace annotation
is needed here. See
[`../../../infrastructure/controllers/staging/reflector/README.md`](../../../infrastructure/controllers/staging/reflector/README.md).

**The namespace needs no PodSecurity exemption.** The lab pods run non-root with a read-only
root filesystem and all capabilities dropped, which satisfies the Talos baseline PodSecurity
that is the cluster default — so `namespace.yaml` carries no PSA opt-out label.

**Database access is read-only and reflected, not copied.** Each lab reads its project's
read-only replica using the CNPG `<db>-app` connection Secret, which is mirrored into `lab` by
reflector: the source CNPG cluster grants the permission
(`apps/staging/databases/<project>/cluster-reflector-patch.yaml`, `reflection-allowed-namespaces:
"lab,database"`) and the chart-generated stub in `lab` requests it. Only the `-app` Secret ever
leaves the project namespace — see
[`../../base/databases/asp/README.md`](../../base/databases/asp/README.md).

## Traps

- **Adding a project takes two edits, in two directories.** Append the name to `projects` in
  `release.yaml` *and* add the reflection permit annotation to that project's CNPG cluster
  (`apps/staging/databases/<project>/cluster-reflector-patch.yaml`). With only the first, the
  chart-generated stub Secret in `lab` stays empty and the pod cannot reach its database. Note
  that `scraper` deliberately does not permit `lab`.
- **`imagePullSecretReflect.source` is `namespace/name` of the central secret**, i.e.
  `reflector/ghcr-pull-secret`. Point it anywhere else and the stub is never filled, so the pod
  cannot pull the private GHCR image.
- **`auth.disableToken: true` means there is no second factor.** The tailnet is the only auth
  boundary; do not expose these Services any other way.
- **Do not add reflect-stub Secrets to `kustomization.yaml`.** The chart generates them; a
  hand-written copy would fight it.
- **Keep the pods baseline-compliant.** There is no PodSecurity label on the `lab` namespace, so
  the cluster default applies (`enforce: baseline`, `warn`/`audit: restricted`, only `kube-system`
  exempt — a talhelper default rendered into the node configs, see
  [`../../../bootstraping/README.md`](../../../bootstraping/README.md)). A lab pod that needed
  privileged mode or a host namespace would be rejected at admission, and would need a PSA
  label added here.
- **The chart is in another repository.** `k8s/charts/lab` lives in `eliorion/asp`, and
  `reconcileStrategy: Revision` means a new commit to that path rolls the labs. The
  GitRepository `ignore` block is what keeps unrelated `asp` commits from doing so.

- **A Helm re-apply empties the reflected pull Secret, and reflector will not refill it.** The
  chart owns `ghcr-pull-secret` and re-applies it as `{}` while leaving the
  `reflected-version` annotation intact, so reflector compares versions, decides the copy is
  current, and logs `Validated 4` — leaving an empty Secret and `401 Unauthorized` on every image
  pull. Hit on 2026-08-24 resuming the suspended release. Fix:
  ```bash
  kubectl -n lab annotate secret ghcr-pull-secret \
    reflector.v1.k8s.emberstack.com/reflected-version- --overwrite
  kubectl -n reflector annotate secret ghcr-pull-secret refresh-trigger="$(date -u +%s)" --overwrite
  kubectl -n lab delete pod --all
  ```
  Check the other three namespaces the source permits (`asp`, `fbref`, `scraper`) with
  `kubectl -n <ns> get secret ghcr-pull-secret -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d`
  — an empty `{}` is the symptom, and only a namespace whose release was re-applied is affected.
## Operating it

Park or wake a single lab, and reach it without the tailnet:

```bash
kubectl -n lab scale deploy/lab-asp --replicas=0        # park it
kubectl -n lab scale deploy/lab-asp --replicas=1        # wake it
kubectl -n lab port-forward svc/lab-asp 8888:8888       # http://localhost:8888
```

With `auth.disableToken: true` there is no token to look up. If the token is ever re-enabled,
it is printed in the pod log:

```bash
kubectl -n lab logs deploy/lab-asp | grep -m1 token
```

Check the tier:

```bash
flux get kustomizations | grep -E 'lab|databases|infra-reflector'
flux get helmreleases -n flux-system lab
kubectl -n lab get pods,svc
kubectl -n lab get secret                               # reflected -app + pull secrets, filled
```
