# clusters/production

## What this is

The Flux entrypoint directory for a production cluster that **does not exist**. No
production Talos cluster has ever been bootstrapped, so nothing in this directory has ever
been reconciled by a running Flux. It is scaffolding: a smaller, older copy of
[`../staging/`](../staging/) that was written in June 2026 and has not been exercised
since. The repository front page says the same thing under
[Known limitations](../../README.md).

Read this before assuming any of it works. It is syntactically valid and it has never been
applied to a live API server. It is not a kustomize root: this directory has no
`kustomization.yaml`, so `kubectl kustomize clusters/production` errors with `unable to
find one of 'kustomization.yaml', 'kustomization.yml' or 'Kustomization'` — the same as
`clusters/staging`, because Flux's kustomize-controller generates one at reconcile time.
What can be render-checked is the overlays it points at, and three of the four do render;
`apps/production` does not (see Traps).

## How it is wired, file by file

Flux's own root Kustomization (`flux-system`, from `flux-system/gotk-sync.yaml`) points at
`./clusters/production` and applies the three YAML files below, which declare six more
Kustomizations.

### `flux-system/`

Generated by `flux bootstrap`. Both manifests carry a `DO NOT EDIT` header and
`gotk-components.yaml` is **byte-identical** to
`../staging/flux-system/gotk-components.yaml`.

- `gotk-components.yaml` — Flux `v2.8.8`, components
  `source-controller,kustomize-controller,helm-controller,notification-controller`.
- `gotk-sync.yaml` — the `GitRepository` `flux-system`
  (`ssh://git@github.com/eliorion/homelab_v1`, branch `main`, `interval: 1m0s`,
  `secretRef: flux-system`) plus the root `Kustomization` `flux-system`
  (`path: ./clusters/production`, `interval: 10m0s`, `prune: true`). Identical to staging
  except for that one `path` line — both clusters would sync the same repository and
  branch.
- `kustomization.yaml` — lists the two files above. This is what `flux bootstrap`
  or `kubectl apply -k` installs.

### `infrastructure.yaml`

Four Kustomizations, in dependency order:

| Name | Path | Interval | Gates |
| --- | --- | --- | --- |
| `infra-certmanager` | `./infrastructure/controllers/base/cert-manager` | `1h` | `wait: true`, health checks on the `cert-manager` and `cert-manager-webhook` Deployments in `cert-manager` |
| `infra-cnpg-plugin` | `./infrastructure/controllers/base/cnpg/plugin` | `1h` | `dependsOn: infra-certmanager`, `timeout: 10m`, `wait: true`, health check on HelmRelease `plugin-barman-cloud` in `flux-system` |
| `infrastructure-controllers` | `./infrastructure/controllers/production` | `1m0s` | `dependsOn: infra-cnpg-plugin`, sops decryption |
| `infrastructure-services` | `./infrastructure/services/production` | `1m0s` | `dependsOn: infrastructure-controllers`, sops decryption |

The two `base/` paths are shared verbatim with staging — this directory does not have its
own cert-manager or barman-cloud-plugin overlay.

`infrastructure/controllers/production` resolves to nothing but `../../base/cnpg/` (the
CNPG operator). `infrastructure/services/production` renders only `cloudflare/` (the base
cloudflared plus `tunnel-secret.enc.yaml`); its `keycloak/` entry is commented out in that
overlay's `kustomization.yaml`.

### `apps.yaml`

One Kustomization, `apps` → `./apps/production`, `interval: 1m0s`, `prune: true`, sops
decryption, `dependsOn: infra-cnpg-plugin`.

Staging splits this tier into three Kustomizations (`databases`, `db-migrations`, `apps`).
Production has one, so the CNPG `asp-db` cluster under `apps/production/databases/` is
swept into the same reconcile as everything else with no ordering guarantee between them.

### `monitoring.yaml`

One Kustomization, `monitoring-controllers` → `./monitoring/controllers/production`,
`interval: 1m0s`, `prune: true`, sops decryption. That path renders the
kube-prometheus-stack base with `grafana-admin.enc.yaml` and a patch setting
`/spec/values/grafana/ingress/enabled` to `false`.

There is no `monitoring-configs` Kustomization here, because `monitoring/configs/` only
contains a `staging/` overlay. A production cluster would get the stack and no
PrometheusRules or dashboards.

### Local files, not in git

`age.agekey`, `kubeconfig` and `.envrc` sit in this directory and are all ignored by the
root `.gitignore` (`*.agekey`, `kubeconfig*`, `*.envrc`). Never commit them. `.envrc` is a
direnv file exporting `RENOVATE_GITHUB_TOKEN`, `GITHUB_TOKEN`, `GITHUB_USER`, `AGE_PUBLIC`
and `KUBECONFIG`; the tokens in it are plaintext and stale, and `KUBECONFIG` still points
at `/workspaces/k3sclusterforlearning/clusters/production/kubeconfig`, a path from before
the repository was renamed. Rotate the tokens and fix the path before this directory is
ever used for real.

## Why it is like this

This entrypoint is a strict subset of staging's, frozen at the point staging outgrew it.
Compared with `../staging/`, production is missing:

- `sources.yaml` — the `GitRepository` objects `asp`, `fbref`, `lab` and `scraper`.
  Helm sources are unaffected: every `base/` directory ships its own `HelmRepository`
  next to its `HelmRelease`, so nothing central is needed for the Helm tiers.
- `lab.yaml` — the analysis-sandbox tier.
- The Kustomizations `infra-arc-controller`, `infra-longhorn`, `infra-cilium`,
  `infra-cilium-config`, `infra-reflector`, `infra-keda`, `infra-keycloak-operator`,
  `infra-keycloak-realm`, `databases`, `db-migrations` and `monitoring-configs`.

The consequence is worth stating plainly: a cluster bootstrapped from this path would come
up with **no CNI and no storage class**. Cilium and Longhorn are wired only in
`../staging/infrastructure.yaml`. What this entrypoint installs is cert-manager, the
barman-cloud plugin, the CNPG operator, cloudflared, kube-prometheus-stack, the `asp-db`
CNPG cluster with its two `ObjectStore`s and its `ScheduledBackup`, and a handful of
Secrets — nothing that makes the cluster schedulable in the first place.

Several of the production overlays are also deliberately inert:
`apps/production/glpi`, `apps/production/linkding` and `apps/production/audiobookshelf`
all render `resources: []`, and `infrastructure/services/production/keycloak` is commented
out.

## Traps

- **`flux-system/gotk-components.yaml` and `gotk-sync.yaml` are generated.** They say
  `DO NOT EDIT` because `flux bootstrap` rewrites them. Change the Flux version by
  re-running bootstrap, not by hand-editing 6437 lines.
- **The `decryption` blocks are load-bearing and fail silently.** Four Kustomizations
  carry one (`infrastructure-controllers`, `infrastructure-services`, `apps`,
  `monitoring-controllers`); three of those paths actually contain a `*.enc.yaml` today —
  `infrastructure/controllers/production` has none yet. Remove or forget the block and
  Flux applies the literal `ENC[AES256_GCM,...]` string as the Secret value: the apply
  succeeds, no controller errors, and the consumer simply misbehaves (for
  `grafana-admin.enc.yaml`, Grafana rejects the admin login with nothing in any log). This
  has already happened twice in staging — `monitoring-controllers` and
  `infra-keycloak-realm`, both written up in [`../README.md`](../README.md). The inline
  note in `monitoring.yaml` is there for that reason.
- **The `sops-age` Secret is per cluster and hand-made.** It lives in namespace
  `flux-system`, is never committed, and must hold the *production* age key. Per the root
  `.sops.yaml`, everything matching `(^|/)production/.*\.enc\.ya?ml$` is encrypted to
  `age1heestkhtxgn5afg9jdww4dpxlk39qztjgcanu8pr4g8usufww36sdx732h`. Staging's key
  decrypts none of it.
- **`apps/production` has no `kustomization.yaml`.** `kubectl kustomize apps/production`
  fails outright, so this tier cannot be render-checked before it is applied. Flux's
  kustomize-controller generates one when a path has none, so it would not necessarily
  error at reconcile time — it would apply whatever the generator sweeps up, which is not
  something anyone has reviewed. Adding an explicit `kustomization.yaml` is the fix.
- **`prune: true` on every Kustomization here, including the root one.** Pointing a live
  cluster at this path deletes anything in those namespaces that is not in git.
- **Both clusters share `main` on the same repository.** `gotk-sync.yaml` differs from
  staging's only in `path`. Bootstrapping this directory against a cluster that already
  runs staging's entrypoint would give one API server two root Kustomizations, both
  pruning.

## Operating it

There is nothing running to operate. If a production cluster is ever brought up, the order
that this directory implies is:

1. Bootstrap Talos and get a working CNI **outside** this entrypoint, or add
   `infra-cilium` and `infra-longhorn` here first. As written, neither is wired.
2. Create the `sops-age` Secret in `flux-system` from the production age key, before any
   Kustomization with a `decryption` block reconciles.
3. Install Flux: `flux bootstrap` against `clusters/production`, or
   `kubectl apply -k clusters/production/flux-system`.

Render checks that work today, from the repository root:

```bash
kubectl kustomize infrastructure/controllers/production
kubectl kustomize infrastructure/services/production
kubectl kustomize monitoring/controllers/production
```

`kubectl kustomize apps/production` does not work; see the traps above.

Once a cluster exists:

```bash
flux get kustomizations
flux get helmreleases -A
```

## Overlays

This directory is the production half of the repository-wide `base/` + `staging/` +
`production/` pattern. It points at four production overlays
(`infrastructure/controllers/production`, `infrastructure/services/production`,
`apps/production`, `monitoring/controllers/production`) and, for cert-manager and the
barman-cloud plugin, directly at the shared `base/` directories with no overlay in
between.

Reference: [`../../documentations/00-bootstrap-cluster.md`](../../documentations/00-bootstrap-cluster.md),
[`../../documentations/01-architecture.md`](../../documentations/01-architecture.md).
